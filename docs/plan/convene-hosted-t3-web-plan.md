# Convene 托管 T3 Web 资源实施计划

日期：2026-10-17
状态：已实施并合入两个集成分支，本机验收及资源收尾完成；SSH 动态链路限制保留。本文是用户明确要求保留的 Convene 集成计划，不提交上游。

## 1. 目标与边界

平台直接提供与已连接 T3 客户端同次构建的 Web 静态资源，浏览器通过平台访问原有 T3 完整界面。首次打开不再逐个通过客户端反向数据通道获取 JS、CSS、字体和图标；新开页面可以复用相同构建的浏览器缓存。

会话、消息、审批、文件、终端及真实执行仍由客户端原生 V2 服务负责。平台继续拥有配对、访问鉴权、项目模块关系及 MCP 授权，不复制一套 T3 业务后端，也不把缓存命中当作客户端在线。客户端离线时不承诺可操作的离线 Web。

本轮包括资源版本匹配、构建和发布接线、静态分发、会话引导、回滚与清理、定向验收；不建设 Service Worker 离线层、浏览器写操作队列、通用资源上传平台或新的多路复用协议。资源代理 409 独立定位，不能以缓存后的成功掩盖原故障。

仅在两个独立开发分支实施，验证后合回各自集成分支，不合并 main、不推送或创建上游 PR。GitHub 构建执行和生产发布另按用户授权开展；本轮可使用本机同源构建验证真实发布链。

## 3. 构建身份与版本匹配

### 3.1 唯一构建输入

在共享构建开始前生成一次构建元数据，供原生服务 HELLO、Web 包和四种安装包共同使用。扩展现有 build-info，而非维护多份手工版本表：

- `build_id`：不可复用的构建身份。CI 使用仓库内固定命名空间加 run ID、run attempt；本机正式候选生成一次唯一构建 ID。重跑共享构建必须新 ID，单纯重打包可复用原共享 bundle ID。
- `version`：用户可见软件版本。
- `source_commit`：真实源码提交。
- 现有集成协议声明；Web 入口文件与 Vite manifest 引用。

不以版本号、提交 SHA 或安装包平台独自判定 Web 相容；同提交不同构建输入也可能生成不同资源。用现有 Vite 内容命名和 manifest 定义文件集合，不新增逐文件哈希台账。正式发布只接受冻结源码构建；开发热更新不冒充发行包。

本轮采用精确 build_id 匹配，暂不建立跨版本兼容区间。构建身份只用于资源定位，不替代原有协议协商、身份认证或权限。

### 3.2 匹配行为

1. 客户端正常连接时报告同源 build_id。复用现有 HELLO 字段；若必须新增字段，按当前控制协议合同处理协商，不偷偷改变字段语义而忽略旧客户端。
2. 平台打开 Web 时用当前在线连接的构建身份查已发布资源，而不是下载页的“最新版本”。
3. 会话引导固定该构建；浏览器的入口和动态分块都来自同一构建目录。
4. 客户端升级或连接切换使原页面与服务构建不同：明确要求重新打开/刷新页面，不静默替换部分资源，不自动重放用户操作；既有执行任务按原 V2 生命周期处理。
5. 多台不同构建的客户端可同时打开，资源按各自身份路由。

旧 `.22` 无精确身份、或匹配包缺失时，保留现有完整 Web 中继作为明确的兼容路径：继续使用该客户端自己的完整资源，不混入平台其他版本。缺包不临时从任意 URL 拉取资源、不把未验证输入注册为发行。平台设置页可给出简短更新提示，常规页面不展示内部版本匹配解释。

兼容路径的退出条件：受支持客户端集合均具有精确身份且部署中均有对应包，再依项目兼容台账裁决删除；不能永久维护两套 Web 实现。

## 4. 静态资源与会话引导

### 4.1 资源职责

采用平台同源稳定路径，例如 `/t3-web/<build-id>/…`，最终路径按既有 gateway 路由核定。路径不包含 Runner ID、会话 ID、用户 ID 或实际部署域名。

- MinIO 保存不可变 Web 发布目录；gateway 使用现有对象存储静态分发模式提供文件。静态请求不经过 Python 会话中继，不调用客户端数据通道。
- 使用 Web 构建的纯静态入口模板生成每次会话 HTML。模板来自匹配包；不继续为了入口 HTML 请求客户端。
- 会话 HTML、跳转、bootstrap 和鉴权响应 no-store；静态文件使用版本化 URL 和 immutable 缓存，按现有服务器能力提供正确 MIME、压缩及条件请求。
- 缺失 JS/CSS 返回真实 404，不能回落 SPA HTML；SPA 路由仍回到会话鉴权和动态入口。
- 只发布浏览器运行必需资源及 manifest/模板；不带服务器代码、凭据、用户数据、私有配置或默认公开 sourcemap。

### 4.2 前端路径拆分

保留会话路由/API/WebSocket 的 base path，新增专属静态资源 base 配置。直连 Web、Electron、本地开发默认行为不变；只有平台托管入口注入版本化资源基路径。

梳理首屏脚本、动态 import、Vite preload、CSS url、字体、图标、Worker/WASM 等实际构建产物，确保整个可达资源依赖图都走静态基路径；不存在的资源类型不另造适配。现有 Vite manifest 是构建产物依赖真源。

初始项目、会话路由前缀和资源基路径由平台引导页注入。原生 bearer 仍只在服务端桥接使用，不写入 HTML 或静态包。MCP、消息、用户文件、下载响应和终端内容不得进入共享资源目录或缓存。

深链接、刷新、草稿、历史进入继续使用当前原生路由。iframe 内完整 Web、单独窗口和客户端原生入口都验收，不能只改首页。

## 5. 发布、安装与回滚

### 5.1 单次构建产物

扩展共享 bundle job，在同一次编译中产生 Web 静态归档和构建元数据；Linux x64 deb/AppImage、Windows x64 exe、macOS arm64 dmg 均消费该 bundle，不在矩阵任务中重新编译出不同 Web。

扩展现有 release adapter，输出四包及一个 Web 包的关联信息。平台发布工具验证 build_id 一致、必需产物完整、入口和 manifest 所引用资源存在；缺包或身份不一致时不切换发行入口。验证文件存在用于防止发布后实际 404，不另算没有消费者的校验和。

GitHub 工件中不得出现实际平台地址、账号或本机路径。部署凭据与目标 origin 从忽略文件或运行环境提供；资源使用相对路径。无需处理已有 Git 历史。

### 5.2 平台发布顺序

1. 复用现有发布工具，将完整包放到不可对外选择的暂存位置。
2. 校验共享身份、入口、manifest 依赖和必要响应行为；失败只清理此次暂存。
3. 将完整不可变目录置为可用，再登记发布索引。已发布 build_id 禁止覆盖；重复发布同一来源按现有幂等合同处理，内容有变化必须新构建。
4. Web 包可用后，才切换对应桌面版本的下载入口。四包整体是否齐备沿用当前发行规则，不把缺少平台包当成完整交付。
5. 原下载 bucket `t3code-clients` 与 ZFile 用户下载入口继续保留；Web 目录走独立受控前缀，不把静态分块展示为安装下载列表。

发布索引与清理使用同一个发行 owner；优先扩展现有发布元数据，不为这次优化新建数据库迁移框架。实施时确认 MinIO 对象可见性和索引切换顺序，保证未完成上传永不被选中。

首次部署先让平台支持新路径及兼容中继，再发布精确匹配 Web 和新客户端。已有安装不被强迫在平台更新瞬间失效。

### 5.3 回滚

保留当前发行和本次回滚发行的安装包、Web 目录及发布输入。切换下载入口不改变已经打开页面的固定资源目录。客户端回退使用对应 Web，平台回退仍可通过原中继打开客户端；不要因回滚删除用户数据或更改原生会话身份。

发布新平台前先在隔离环境演练失败上传、未切换索引和版本回退。正式生产切换不包含在“计划落盘”授权内。

## 6. 清理与版本保留

静态资源不是普通可随时删除的构建缓存：已打开页面可能稍后才加载某个分块。

- 始终保护当前发行、本次回滚发行、仍声明支持的客户端构建及有效 Web 会话所引用构建。离线客户端也可能回来，不只查询当前在线连接。
- 支持集合来自发行策略及实际登记引用，不从“最近两次构建”猜测。历史浏览器缓存不是资源备份。
- 停止支持某构建时，先关闭新托管会话入口并明确其兼容路径/升级行为；有效旧会话结束或按现有期限失效后才删除其目录。已有失效页面再次请求时引导重新进入，不返回其他构建的分块。
- 不无限延长旧会话或增加独立租约系统。复用既有会话有效期和发行 owner；清理与发布串行执行，删除前复查保护引用。
- 清理命令先列出确切 build_id、对象前缀、体积和保留理由，删除只针对这些对象；禁止按模糊前缀清 bucket 或 Docker prune。
- 暂存失败工件、独立测试 bucket、浏览器数据及冻结源码副本，在取回必要证据后及时清理。实际被验收服务引用的包和镜像保留，临时 SSH 体验结束按既有恢复流程关闭。
- CI 中间工件短期保留；成功发行所需安装包/Web/发布元数据必须已转入持久发行存储，不能依赖 Actions 临时工件长期可下载。
- 输出实际删除与保留清单、失败对象及后续处理。空间不足不能删除生产引用资源或拿当前回滚包腾空间。

## 7. 分阶段实施与提交

建议分支：T3 `codex/hosted-web-assets`、平台 `codex/t3-hosted-web-assets`，分别从当时集成 HEAD 建立独立工作区，已有同名分支先检查再复用。

1. **合同与基线**：记录实际源码、运行候选和冷加载资源请求；确认发行工具、会话期限、协议兼容边界。将本计划及当前决策纳入 Convene 分支文档。
2. **T3 构建与路径**：共享 build-info、精确 HELLO 身份、静态/会话基路径分离；产出本机真实候选。单独提交。
3. **发行接线**：共享 job 导出 Web，adapter 和平台 publisher 接受一致产物；实现不可变发布、清理及回退规则。按仓库分别提交。
4. **平台托管入口**：身份解析、资源可用性选择、动态 HTML、gateway 静态路由；保留明确旧构建中继，补齐匹配与过期行为。单独提交。
5. **409 定位**：保留响应正文/错误码与请求 owner 的关联证据，排除人工重载取消；若是受支持场景的真实缺陷，在其所属边界修复和提交，不靠延长通用超时或重放写请求消除日志。
6. **冻结候选与验收**：相关测试、类型/lint、真实构建通过后合入两个集成分支；先确认无活动任务并备份，再更新本机客户端和验收容器。候选号选择 `.22` 后实际未占用版本。
7. **交付与收尾**：补记录截图、测量、失败与限制，清理临时资源；不合并 main、不创建 PR。没有授权时不推送或执行生产发布。

本计划已按下列记录执行；Actions 及本机下载演练补充见第 11 节，生产发布和其他系统安装仍另行验收。

## 8. 验证标准

只执行能区分真实行为的检查；每项失败直接回到对应 owner 修复，不追加泛化门禁。

| 场景         | 通过标准及失败处理                                                                                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 冷启动无缓存 | 匹配包存在时，干净浏览器首次进入不为静态资源创建客户端数据通道；入口模板同样不依赖客户端 HTTP。记录静态请求数/字节、动态通道数、首屏可操作时间；失败检查构建路径遗漏。 |
| 缓存与新会话 | 同构建新 SID 使用相同资源 URL；刷新、深链接、延迟加载分块成功，未缓存会话 HTML。失败检查 base path 和响应头。                                                          |
| 资源闭包     | 真实 bundle 的动态 import、CSS 与实际 Worker 等资源全部可达；404 不返回 HTML。失败修正打包/发布缺失，不用 SPA fallback 掩盖。                                          |
| 版本         | 两种真实构建、相同软件版本不同 build_id、旧 `.22`、缺包、升级中旧页面与回滚行为符合第 3 节；不能以受控假安装包宣称四系统安装通过。                                     |
| 发布与清理   | 半途上传不被选择、身份不匹配拒绝、相同 build_id 不覆盖；活跃/支持/回滚资源保留，退役且无有效会话引用资源才删除。使用独立 bucket 验证，不操作生产。                     |
| 网络         | 直连与现有 SSH 路径分别测干净冷启动、热缓存及动态交互；慢/断开的客户端不会拖慢平台静态资源，真实业务断连如实呈现。409 不记为通过。                                     |
| 权限         | 无会话授权不能调用业务 API；跨用户/项目不能借静态包访问会话；断开、会话过期与重新进入按现有合同。静态包不含会话配置或私有地址。                                        |
| 原生回归     | Electron、直连 Web、开发模式正常；移动端涉及共享合同则做相关检查，不声称移动端实机验收。                                                                               |
| 业务联动     | 配对、绑定、MCP 权限、历史、草稿、发送/继续/停止/审批、文件和终端、完整 Web 新窗口/刷新。真实推理仅 Luna，在独立测试目录，不使用 Convene 开发目录。                    |
| 页面         | 桌面和窄窗口、长项目名、首屏加载、版本失配/过期、缺包兼容入口截图；控件可达，无内部实现解释堆叠。                                                                      |

先跑改动范围的受控协议、发布/清理及路由测试，再进行一次冻结候选真实 UI 联动。性能在同条件下报告前后原始结果，不凭单次 SSH 测量制定任意秒数 KPI，也不以缓存通过替代真实业务验证。真实 Windows/macOS 安装缺环境时明确未覆盖。

## 9. 长期记录与完成标准

长期合并决定统一记录于 `docs/operations/convene-fork-maintenance.md`：用户需求、当前决策、理由、职责、来源提交、验证边界和上游合并取舍。平台更新 Runner 运行/控制协议合同与实际发行运维文档；计划只记执行进展，不成为第二套协议真源。

上游有等效静态托管/构建标识时优先复用并删除定制；上游改变内部路由时迁移资源/会话职责，不保留旧结构阻止升级。不能恢复随意 latest 混配、私有地址内嵌或把用户响应放进静态缓存。

完成需具备：两个集成分支的逐步提交记录、同源四包/Web 构建链与真实本机发布证据、客户端/资源精确匹配、首次静态零中继、业务联动与缓存/回退/清理验收、更新后的本机环境及截图。实际未执行的 GitHub 构建、其他系统安装或生产发布逐项说明；不以计划、模拟工件或最终偶尔加载成功代替交付。
